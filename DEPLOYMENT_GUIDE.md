# Deployment Guide

TruthLens is a stateful Express app (MongoDB session store, file uploads, server-rendered EJS). It deploys cleanly to **Docker, Render, and Railway** (all long-running Node processes). **Vercel and Netlify** are also supported via serverless wrappers, but come with real trade-offs — read that section before choosing them.

Every option needs, at minimum, the environment variables in `.env.example` — especially `MONGODB_URI` (use [MongoDB Atlas](https://www.mongodb.com/atlas) for any non-Docker-Compose deployment), `JWT_SECRET`, `JWT_REFRESH_SECRET`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`, and `GROQ_API_KEY`.

---

## Option 1: Docker (recommended for self-hosting / VPS)

```bash
cp .env.example .env   # fill in real values
docker compose up --build
```

This starts the app **and** a MongoDB container (`docker-compose.yml`), with the app's `MONGODB_URI` automatically pointed at the bundled Mongo. Data persists in the `mongo_data` and `uploads_data` named volumes across restarts.

To run just the app image against an external MongoDB (e.g. Atlas):

```bash
docker build -t truthlens .
docker run -p 5000:5000 --env-file .env truthlens
```

The image runs as a non-root user and exposes `/health` for `HEALTHCHECK`/orchestrator probes.

---

## Option 2: Render

1. Push the repo to GitHub/GitLab.
2. In Render: **New → Blueprint**, point it at the repo — it will read `render.yaml` and provision a Docker-based web service automatically.
3. In the Render dashboard, fill in the `sync: false` env vars (`MONGODB_URI` from Atlas, `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `GROQ_API_KEY`, `EMAIL_USER`/`EMAIL_PASS`, `BASE_URL` = your Render URL). `JWT_SECRET`/`JWT_REFRESH_SECRET` are auto-generated by the blueprint.
4. Render uses the `/health` endpoint (configured in `render.yaml`) to know when the deploy is healthy.

Render has no managed MongoDB — use Atlas's free tier.

---

## Option 3: Railway

1. `railway login && railway init` (or connect the GitHub repo in the Railway dashboard).
2. Railway reads `railway.json` and builds from the `Dockerfile` automatically.
3. Add a MongoDB plugin from the Railway marketplace, or point `MONGODB_URI` at Atlas.
4. Set the rest of the env vars in the Railway dashboard (Variables tab).
5. Railway's health check is configured to hit `/health` with a 30s timeout and restarts on failure (up to 5 retries).

---

## Option 4: Vercel (serverless — read the caveats)

`vercel.json` + `api/index.js` wrap the same Express app with `serverless-http`, routing every request through one serverless function.

```bash
vercel --prod
```

Set all `.env.example` variables in the Vercel dashboard (Project → Settings → Environment Variables).

**Caveats specific to Vercel:**
- **File uploads will not persist.** `multer`'s local-disk fallback writes to the function's ephemeral filesystem, which is wiped on the next cold start (and isn't shared across concurrent invocations anyway). **Set `CLOUDINARY_*` env vars** — the app already prefers Cloudinary when configured (`authController.uploadPhoto`), so this "just works" once the keys are set, but it is not optional on Vercel the way it is on Docker/Render/Railway.
- Cold starts add latency to the first request after idle; `config/database.js`'s `connectDB()` is idempotent and reused across warm invocations to minimize this, but the very first hit after a cold start will be slower.
- `express-session` + `connect-mongo` still work (they just talk to Atlas), but a session-heavy design isn't the best fit for serverless in general — this app's actual auth (JWT) doesn't depend on server-side sessions, so this mostly affects CSRF-protected form pages.
- `vercel.json`'s `includeFiles` explicitly bundles `views/**` and `public/**`, since Vercel's function bundler only auto-traces `require()`'d files, not the `views`/`public` directories Express reads from disk at runtime. If you add new top-level static/view directories later, add them here too.

## Option 5: Netlify (serverless — read the caveats)

`netlify.toml` + `netlify/functions/api.js` (same `serverless-http` pattern as Vercel).

```bash
netlify deploy --prod
```

Set env vars in Netlify dashboard (Site Settings → Environment Variables).

**Caveats specific to Netlify:**
- Same **file upload / Cloudinary requirement** as Vercel — see above.
- `netlify.toml` sets `publish = "public"`, so static assets under `public/` are served directly by Netlify's CDN (fast, and offloads traffic from the function); everything else is redirected to the function via `/* → /.netlify/functions/api/:splat`.
- The function strips its own `/.netlify/functions/api` path prefix (`serverless-http`'s `basePath` option) so Express sees normal paths like `/` and `/api/auth/login` — if you rename the function file, update `basePath` in `netlify/functions/api.js` to match.
- Netlify Functions have a default 10-second execution timeout (26s on some plans) — fine for this app's request patterns, but worth knowing if an AI provider call is unusually slow.

---

## Post-Deploy Checklist (any platform)

1. Confirm `/health` returns `200 { status: 'ok' }`.
2. Log in with `ADMIN_EMAIL`/`ADMIN_PASSWORD`, then **change the admin password immediately**.
3. Set `BASE_URL` to your real deployed URL (used in verification/reset email links).
4. If you didn't set `NEWS_API_KEY`, the live trending feed will be empty — the curated (admin-managed) trending workflow works regardless.
5. Toggle Maintenance Mode on/off once from Admin → Settings to confirm it actually gates non-admin traffic on your deployment (see `SECURITY_REPORT.md` / `TESTING_REPORT.md` for what this checks).
